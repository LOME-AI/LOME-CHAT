# Task 18 — Sender on billed rows — impl report 1

## Objective

`usage_records` records payer and sender independently: a schema change adding the
sender reference (FK, indexed, `SET NULL` on deletion), the charge write path
threading sender identity through settlement, and the db shape-test registry
updated. Structure-only migration (ZERO-users ruling — no backfill).

---

## DECISION — sender shape: two nullable columns (`sender_user_id` + `sender_link_id`)

The brief flagged this as the design question to resolve and justify. Research §3
is the binding constraint: `settlementSenderId` returns **a member's `userId` OR a
link guest's `linkId`** (`settlement.ts` comment: "a member's userId, a link guest's
linkId — never the paying owner"). A single users-FK column cannot hold a `linkId`.

**Chosen:** two nullable columns, exactly one written per row —
`sender_user_id uuid → users(id) ON DELETE SET NULL`, and
`sender_link_id uuid → shared_links(id) ON DELETE SET NULL`. Both partially indexed
(`WHERE … IS NOT NULL`).

**Why this and not the alternative (single nullable `sender_user_id`, guests NULL,
guest recovery via the message row):**

1. **It is the only shape that satisfies the plan's own acceptance criterion.** The
   criterion requires an integration test proving `sender = member/guest principal`.
   Under the single-column option a guest turn records NULL, so "sender = guest
   principal" is unprovable on the row — the criterion would be unimplementable as
   written, and BILLING §Group Funding 3 ("**Sender and payer are first-class on
   every billed row** — `usage_records` records both, independently queryable")
   would remain false for exactly the case the task exists to fix.
2. **It removes the defect research §3 named**, rather than half-removing it.
   Research §3 documents that recovering "which guest caused this charge" today
   "requires a non-FK, application-level join": `usage_records.contentItemId →
   content_items.messageId → messages.batchId` → find the sibling `senderType='user'`
   row → read its `senderId`. Leaving guests NULL preserves that join for guests —
   the harder half of the problem — so the fragile path would survive.
3. **The schema precedent is direct and in-repo**, so this invents no new pattern.
   The brief permitted a linkId column only if precedent supports it. It does, and
   more strongly than `shared_messages`: `conversation_members`
   (`conversation-members.ts:28-29`) carries **exactly this pair** — nullable
   `userId → users` and nullable `linkId → shared_links`, both `SET NULL`, both
   partially indexed — to model the same user-or-guest principal. The sender of a
   turn *is* a conversation member principal, so this mirrors the table that already
   owns that concept. (`shared_messages.linkId` is a weaker precedent — I did not
   rely on it.)
4. **`SET NULL` on both keeps the pseudonymization doctrine exact.** The financial
   row survives hard deletion of either principal; only the reference is scrubbed
   (Art. 17(3)(b) retention), matching the existing `userId`/`contentItemId`/
   `conversationId` columns on this table.

**Cost accepted:** a both-null row is legal at the DB level (it is the *pseudonymized*
state, so a CHECK constraint forbidding both-null would be wrong — it would break
deletion). Insert-time exactly-one-ness is enforced in the type system instead: the
domain `ChargeSender` is a discriminated union, so the adapter can only ever write one
side. Documented in the schema comment.

**Not done (deliberate, out of scope):** no `conversation_members.id` column. The
member-row id already rides `member_budgets.memberId`; adding a third sender
reference would be an unplanned FK with no criterion behind it.

## Tests added (name — behavior — criterion covered)

**db shape registry (criterion 3):**

- `records a member sender via a nullable users FK severed on deletion` — column is
  uuid, nullable, FK onDelete `set null` → FK/SET NULL criterion.
- `records a link-guest sender via a nullable shared_links FK severed on link
  deletion` — same, plus asserts the foreign table is `shared_links` → the decision.
- `indexes both sender columns partially (IS NOT NULL) for sender-keyed queries` →
  "indexed" criterion.
- `shape-fk-indexes.test.ts` + `schema.integration.test.ts` partial-index allowlists
  extended (both new indexes are `IS NOT NULL` partials; the integration test verifies
  the predicate against live `pg_indexes` — it passed, so the migration's predicate is
  real, not just declared).

**Charge write path (criterion 2):**

- `records the payer and a member sender independently on the usage record` —
  payer column = wallet owner, sender column = the member.
- `records a link-guest sender as the link principal with no sender user` —
  `senderLinkId` set, `senderUserId` NULL.
- `severs the sender on user deletion via SET NULL, keeping the charge row intact` —
  asserts the value is present **before** the delete, then NULL after, with the row
  and its `costNanoUsd` intact → deletion semantics, pinned by real user deletion.
- Engine: `threads a member sender onto every charge of the run (payer and sender
  independent)` (multi-charge — both siblings carry it) and `threads a link-guest
  sender as the link principal, never a user id`.

**End-to-end settlement (criterion 2, the criterion's named cases):**

- `owner-funds a link-guest turn: …` (existing test, extended) — now also asserts the
  billed row is `{ userId: owner, senderUserId: null, senderLinkId: link }`.
- `owner-funds a member turn: records the owner as payer and the member as sender` —
  the owner-funded **member** case.
- `self-funds a solo turn: records the same principal as both payer and sender` —
  the "self-funded records both self" case.

## Deviations

1. **Files touched beyond the plan's Files list**, all forced by the contract change
   and sanctioned by A3 (T03/T04 precedent): `billing/ports/stores.ts`,
   `billing/adapters/stores.ts`, `billing/domain/index.ts`, `billing/index.ts`
   (the `UsageRecordInput`/`ChargeSender` surface), and
   `packages/db/src/schema/relations.ts` + the two partial-index allowlists
   (`shape-fk-indexes.test.ts`, `schema.integration.test.ts`) — a new FK
   *must* be registered in those or their own gates fail. No behavior added anywhere
   beyond what the sender columns require.
2. **`ChargeInput.sender` is required, not optional.** An optional field would let a
   caller silently omit the sender and lose the attribution the task exists to add;
   required means the compiler enumerates every producer (there are two). This is
   what made the A3 sweep exhaustive by construction.
3. **`relationName` added to the pre-existing `usageRecords.user` relation.** Not
   cosmetic — drizzle cannot disambiguate two FKs to `users` from one table without
   it, so the existing relation had to be named when the sender relation landed.
   `shape-relations.test.ts` (which runs drizzle's own extraction) is green.

## Concerns and limitations

- **Both-null sender rows are legal** and indistinguishable from "sender deleted".
  This is deliberate (see decision, cost accepted) — insert-time exactly-one-ness is
  a type-level guarantee, not a DB constraint. If a future auditor wants a DB-level
  guarantee it must be `NOT (both non-null)`, never `NOT (both null)`.
- **No backfill**, per the ZERO-users ruling: existing rows (dev/seed data only)
  carry NULL senders. The migration is structure-only.
- **Sender is not yet read anywhere.** This task writes the columns and pins them;
  no query or admin read consumes them yet, so `knip`-style unused checks may see the
  new relations as consumer-less until a reader lands.
- **Dev seed rows carry no sender** (see sweep) — cosmetic in dev-only analytics.
- The api and db suites are currently noisy from at least three concurrent lanes
  (notifications, prompt/cassette, T13); every gate above was re-run to separate
  signal from that noise.

## Confidence

**High** for the schema, the write path, and the deletion semantics: every criterion
has a red-first test, the migration's index predicates are verified against live
`pg_indexes`, the drift gate is clean, repo-wide typecheck and `arch:check` are
green, and all four owned test files pass post-format.

The **sender-shape decision** is the one judgment call. I rate it high rather than
certain: it is forced by the plan's own criterion and backed by an exact in-repo
precedent (`conversation_members`), but it commits the schema to two columns where a
future reader might prefer one polymorphic principal column — which the repo does not
do anywhere today.
