# Task-04 — mint shareSecret once per logical mutation

## Objective

Fix the idempotent-replay key-material mismatch: `useMessageShare.mutationFn` re-minted a
random `shareSecret` on every TanStack retry while the `Idempotency-Key` stayed stable, so
the server dedup kept attempt-1's stored wrap but the client URL fragment carried attempt-2's
secret → `openShare(S2, wrap(S1))` produces a garbage content key and AEAD fails (2 sharing
e2e failures). Same latent shape assessed for `useCreateLink` / `useChangeLinkPrivilege`.

## Mechanism of fix

The root cause is a mint-per-attempt of client key material inside a retried `mutationFn`.
The established discipline for the sibling problem (the `Idempotency-Key` itself) is
`idempotencyKeyFor(variables)` in `apps/web/src/lib/idempotent-mutation.ts` — a `WeakMap`
keyed on the stable `variables` object reference TanStack re-passes on every retry, so the
value is minted once per logical `mutate()` and reused across attempts, collected with the
variables object.

Applied the identical pattern to the share secret: a module-level
`shareByVariables = new WeakMap<object, CreateShareResult>()` with a `mintShareOnce(input,
contentKey)` helper. `createShare(contentKey)` (which internally calls `randomBytes(32)`) now
runs exactly once per logical mutation; retries reuse the same `{shareSecret, wrappedShareKey}`,
so the wire wrap and the URL-fragment secret are attempt-invariant and the retry's fragment
opens the first attempt's stored wrap.

`useCreateLink` / `useChangeLinkPrivilege` (and `useRevokeLink`): assessed — these hooks do
NOT mint key material inside `mutationFn`. The link key material (`linkPublicKey`,
`memberWrap`, and the epoch `rotation` wraps) is generated by the caller
(`invite-link-modal.tsx` → `rotation.ts`) and passed in as part of the stable `input`
variables object; `mutationFn` only reads `input` and attaches `idempotentHeaders(input)`.
Therefore they are already retry-safe by construction — the mint-once site is the caller, and
the variables reference is stable across retries. No production change was needed there; the
latent-shape risk is guarded by a contract test (below) so a future regression that moves a
mint into the `mutationFn` fails at merge.

## Enforcement rung (AC-3)

The two forced-retry contract tests ARE the enforcement rung — they live in the web unit
suite so drift (a re-minted secret or a changed payload across retries) fails at merge.

A lint/arch rule "ban re-randomizing key material inside an idempotent `mutationFn`" was
assessed and judged **not cleanly feasible** and not added, for these reasons:

- The defect is a data-flow property (a randomness source — `randomBytes` / `createShare` /
  `crypto.getRandomValues` — whose result flows into the request body or URL while the
  idempotency key is held stable), not a syntactic one. ESLint's AST scope and the ts-morph
  structural harness cannot express "this value is re-derived per retry but must be stable"
  without real taint analysis.
- A blunt syntactic proxy ("no call to a known-random function lexically inside a `mutationFn`
  arrow") would be both over- and under-inclusive: it would false-positive on legitimately
  per-attempt randomness (e.g. a fresh nonce that SHOULD vary) and miss randomness pulled in
  via a helper. That is a worse signal than the precise contract tests.

If the orchestrator wants a rung beyond the contract tests, the tractable option is a
convention (all client key material minted in the caller / `onMutate`, never in `mutationFn`)
plus these tests — not a static rule. Raised for a ruling; not implemented.
