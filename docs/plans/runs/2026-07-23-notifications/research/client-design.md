# Client architecture — analyst decision material (2026-07-24)

Authoritative for implementation briefs. Founder rulings that constrain this: one-time
"enable notifications?" surface (no smart/value-moment priming — rejected, do not
relitigate); everything follows explicit settings; no per-device management UI; generic
payloads (client renders generic text + deep-links).

## Verified baseline

- apps/web is a plain Vite SPA: no SW, no manifest, no PWA plugin (`vite.config.ts`
  plugin list 154–173 all custom/local; `public/` has only `_redirects` + `assets/`).
- Native push: Capacitor FCM, ask-on-mount (`capacitor/hooks/use-push-notifications.ts:23-31`);
  token registration + tap deep-link with UUID-regex hardening in
  `capacitor/provider.tsx:42-63` (validator inline at `provider.tsx:21`).
- Realtime is strictly per-conversation (refcounted socket per open conversation,
  `lib/conversation-socket-registry.ts`); NO user-level socket, NO cross-conversation
  event source, NO unread/badge/title/sound code anywhere.
- Server presence suppression already ships (`domain/push-recipients.ts:15-23`).
- Prod CSP `default-src 'self'`, no `worker-src` — same-origin SW admissible without CSP
  change (`apps/web/dist/_headers:44`; headers are GENERATED by `headersPlugin`,
  `vite.config.ts:171` — changes go in the headers source, never dist).
- Capacitor WebView on `http://localhost`, `presentationOptions: ['badge','sound','alert']`.
- UI kit exports `Switch`, `RadioGroup`, `Select`, `DropdownMenuSub/SubTrigger/SubContent`,
  `Dialog` (`packages/ui/src/index.ts:55-84`). Mute today = binary `DropdownMenuItem` in
  `components/sidebar/chat-item.tsx:101-108`.
- Announcements banner = shipped precedent for a dismissible surface
  (`hooks/announcements/use-banner.ts`).
- iOS Safari push requires an installed (Home Screen) PWA + manifest; `setAppBadge` is
  installed-PWA/desktop only, absent on Android browsers.

## 1. Service worker — RECOMMENDED: hand-rolled push-only SW + hand-written manifest

`src/sw/sw.ts` in TypeScript (WebWorker lib types), compiled to a STABLE UNHASHED
`/sw.js` (small second Vite build config or dedicated rollup input with fixed
`entryFileNames` — hashed output unusable; the SW URL is its identity). Handlers:
- `push` → validate payload with shared Zod schema from `@hushbox/shared` →
  focused-client check → `showNotification` or `postMessage` to the focused client.
- `notificationclick` → `clients.matchAll` focus-or-`openWindow(/chat/:id)` using the
  SAME conversation-id validator as the Capacitor tap handler — HOIST the validator from
  `provider.tsx:21` to `@hushbox/shared` first (One Implementation, Shared).
- NO `fetch` handler, NO precache — the SW does push only; can never serve stale assets
  or become a second update mechanism (vs HTTP caching and `@capgo/capacitor-updater`).

Also hand-write `public/manifest.webmanifest` (name, icons, `display: standalone`,
`start_url`) — without it iOS has ZERO push path and `setAppBadge` never renders. Side
effect: the app becomes installable (founder nod obtained in design round).

Registration: `registerPushServiceWorker()` called only when `!isNative()` (in the
Capacitor shell FCM is the delivery path; a SW would create two push paths on one
platform). Gate via the env module pattern, not raw `import.meta.env`. `dist/_headers`
gains `Cache-Control: no-cache` (or short max-age) for `/sw.js` via the headers source.

REJECTED: `vite-plugin-pwa` injectManifest (Workbox dep + update machinery = second
asset-delivery mechanism, banned smell) and generateSW (unownable generated code where
push correctness lives).

## 2. Subscription lifecycle — RECOMMENDED: typed web registration, not token-string smuggling

Dedicated web-subscription registration through the notifications slice (discriminated
union on the existing route or a new route) with Zod schema
`{endpoint, keys: {p256dh, auth}}`, unique on endpoint, `byUpsert` idempotency (same
class as the token route, `notifications/routes.ts:42-62`). Storage shape ruled
server-side: extend `device_tokens` (see server-pipeline-design.md §2).

Lifecycle:
- Subscribe only after explicit grant (one-time prompt or settings toggle — NEVER on
  mount): `pushManager.subscribe({userVisibleOnly: true, applicationServerKey: VAPID_PUBLIC_KEY})`;
  key from env.config registry via `VITE_` var, never hardcoded.
- Re-register on every authenticated app start (fire-and-forget, same pattern as FCM
  token registration in `provider.tsx:42-53`): `getSubscription()` → POST if present.
  Self-healing via re-run of the one upsert mechanism.
- `pushsubscriptionchange` in SW: re-subscribe with stored key, POST from the SW via
  same-origin fetch `credentials:'include'`. ASSUMED: iron-session cookie is
  same-origin-visible to the SW (verify against deploy topology/`getApiUrl()`); fallback:
  postMessage to open client + next-app-start re-registration, with server 404/410
  pruning as the designed backstop.
- Unsubscribe on logout and global-switch-off: `subscription.unsubscribe()` + typed
  DELETE, best-effort; server 404/410 pruning is the recovery for crash/offline (one
  mechanism per failure class, not a banned backup).

REJECTED: smuggling `JSON.stringify(subscription)` through the token string column
(type-safety + fail-fast violation; unstable key order under uniqueness).

## 3. One-time enable prompt — RECOMMENDED: inline dismissible surface + localStorage + one facade

One-time dismissible inline callout in app chrome (sidebar footer or above composer),
"Enable" → permission request → subscribe; "Later" → dismisses forever, copy points to
Settings. Static inline region, keyboard-reachable, `role="status"`, no focus-stealing
modal; reuses the announcements-banner visual language.

"One-time" persistence is DEVICE-LOCAL (`localStorage`, e.g. `hb:notif-prompt-dismissed`)
— semantically correct because browser permission is per browser/device; a
server-persisted flag would wrongly suppress the prompt on a fresh browser. Additional
suppressors: never render when `Notification.permission !== 'default'`, when no push path
exists (`'PushManager' in window` gate — iOS non-installed Safari), or when the global
notifications setting is off.

One facade, two adapters: client-side `notificationChannel` module with
`getPermissionState() / requestPermissionAndRegister() / unregister()`; web adapter
(Notification API + PushManager + SW registration) and native adapter (Capacitor
`PushNotifications`), selected by `isNative()`. Prompt state machine, settings interplay,
registration POST are shared; platform calls stay per-adapter (complementary, not
duplicate). This REMOVES the ask-on-mount in `use-push-notifications.ts:28-31` and moves
native `requestPermissions()` behind the same gate. Tap-deep-link/token-listener wiring
in `provider.tsx` stays native-only (SW `notificationclick` is its web sibling; only the
hoisted validator is shared).

REJECTED: settings-only (contradicts founder ruling, poor discoverability); modal on Nth
session (founder-rejected smart timing; focus-trap anti-pattern).

## 4. Foreground layer — RECOMMENDED: source-agnostic store; feed per founder ruling

No client-side source of cross-conversation unread exists. Options presented to founder:
(A) client-observable events only (zustand store fed by open-socket frames while hidden +
SW postMessage; cleared on focus/visibility — an "activity since you looked away" badge,
zero backend, reopens to zero); (B) full server-authoritative unread (new realtime
surface — out of client scope, named follow-up); (C hybrid, orchestrator-added) —
`lastReadSeq` cursor already exists in the dismissal design, so the conversations list
can return server-truth unread counts at fetch time, with client-observed increments
between fetches. FOUNDER RULING (2026-07-24 round 3): pending — see plan.md once ruled.
Store interface (`unreadCount`, `markAllSeen()`) stays source-agnostic either way.

Presentation sinks (one store, three sinks):
- Tab title: single effect prefixing `(n) `; must remain the ONLY title writer by rule.
- `navigator.setAppBadge(n)`: feature-detect, skip where absent; `clearAppBadge()` on
  markAllSeen; Safari `setAppBadge(0)`-hides-badge quirk noted.
- Sound: opt-in setting, default off; play on in-app notification arrival only; the
  settings-toggle interaction is the autoplay-unlocking gesture (Assumed — verify);
  never the sole signal (badge + `aria-live="polite"` region carry the same info).

Focused-tab suppression is layered, not duplicate: (1) server presence suppression
(primary, already ships); (2) SW display-time check for the in-flight race —
`clients.matchAll({type:'window'})`; if a focused client exists, postMessage + skip
`showNotification`. ASSUMED: Chromium levies no penalty for skipping when a focused
same-origin client exists — pin by manual test.

REJECTED: polling the conversations list on interval (serverless cost + drift, quiet
second mechanism).

## 5. Settings surface — RECOMMENDED: Notifications Card on /settings + DropdownMenuSub mute

New "Notifications" `Card` on the existing single-page `/settings`, built as
`components/settings/notifications-card.tsx` following the `MailingListCard` precedent
(`settings.tsx:204-304`). Global switch → `Switch`; three per-category `Switch` rows
(messages / run completions / membership) with proper labels; quiet hours → two `Select`s
(hour granularity; no TimePicker primitive exists — prefer Select over a new primitive);
`fieldset/legend` for the quiet-hours group; TanStack Query hooks on the typed client
per the per-hook-file key-factory convention.

Per-conversation mute tiers: `DropdownMenuSub` inside the existing three-dot menu —
"Mute" → `1 hour / 8 hours / 1 week / Forever`, single "Unmute" item when muted. Client
sends a duration; server returns `mutedUntil`; the client renders mute state from the
server value, never computes expiry locally.

REJECTED: dedicated `/settings/notifications` route (speculative structure); dialog +
RadioGroup mute (heavier, unjustified).
